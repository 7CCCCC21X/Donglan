# 规则吃单 · 独立服务（Google Cloud 东京）

把 [huice](https://github.com/7CCCCC21X/huice)（TG 合约昨收偏离提醒机器人）1.154.27 里的**规则吃单**（`rules.py`，`RULE_TAKER`）单独拿出来，做成一个只干这一件事的服务，部署在 Google Cloud 东京（`asia-northeast1`），目的是**吃单更快**。

规则、价格、份数、变量名、记录格式、所有保护措施都和 huice 一样（Railway 上的设置可以直接抄过来）；改的是“怎么跑”：

- **独立进程**：不再和原策略、预挂、复盘页挤在同一个事件循环里。huice 自己的记录里，盘口到了以后被主循环别的活儿占住的时间有 111 ms、2098 ms、2540 ms（σ 重算、复盘页重算、垃圾回收、几万条预挂记录）——这些在这里都不存在。
- **部署在东京**：huice 11-18 实测，机器人在阿姆斯特丹（`europe-west4`），到 Cloudflare 入口只要 7–31 ms，读一次盘口却要 233–311 ms：入口很近、Predict 的服务器很远。东京到它近得多，部署后用 `rt.sh latency` 量真实数字。
- **Rust 写的（3.0 起）**：同一台机器上实测，推送帧到达 → 下单请求交给网络 **0.07 ms**（预先签好）/ **0.12 ms**（当场签名）；原来的 Python 版是 0.31 ms / 0.90 ms。见“[Rust 版](#rust-版30)”。
- **路上的每一步都更短**（见下面“提速”）。
- **有自己的网页控制台和复盘页**（huice 控制台“规则吃单”一组、复盘页“规则吃单”一节的对应物）：看状态、暂停 / 恢复、切模式、在线改规则价格和份数；按规则、按日期复盘，抢单记录、盘口观察、累计盈亏曲线、导出 CSV。见“[控制台和复盘页](#控制台和复盘页)”。

> 先说清楚：这里只有“规则吃单”。原策略、预挂、提醒仍然在 Railway 上的 huice 里跑。原来的 Python 版留在 `python/` 目录当备用，一条命令就能换回去（记录、设置两边通用）。两边怎么配合见“和 Railway 上的 huice 一起用”，**一定先看**。

## Rust 版（3.0）

3.0 起服务是 Rust 写的（`src/`），逻辑逐行照 Python 版（2.0，`python/ruletaker/`）移植，记录格式、设置、网页控制台、Telegram 命令、`rt.sh` 的用法都不变。

**快了多少**（同一台机器，`cargo test --release bench_hot_path -- --ignored --nocapture` 和 `python python/tests/bench_hotpath.py`，记录里都已有 600 场）：

| 推送帧到达 → 下单请求交给网络 | Python 版 2.0 | Rust 版 3.0 |
|---|---|---|
| 预先签好的单 | 中位 0.31 ms | 中位 **0.07 ms** |
| 当场签名 | 中位 0.90 ms | 中位 **0.12 ms** |

说实话：这省下的是 0.2～0.8 ms；一次到 Predict 的网络往返是几毫秒到几十毫秒，**决定抢不抢得到的仍然主要是网络**（所以才部署在东京）。Rust 版的好处还有：没有垃圾回收停顿；同一个回合里从收到推送到请求字节写进网络连接，中间不会被别的任务插队；内存占用小、启动快。

**和 Python 版逐字节一致的地方**（`src/parity.rs` 用 Python 版生成的数据 `tests/vectors/` 核对）：两年里每条规则的每一场、CME 日历、市场标题核对、订单签名（普通钱包和 Predict 智能账户的 Kernel 包装）、登录签名、下单请求体的每一个字节、订单金额的取整。

**比 Python 版多做的两件事**：

- 复用连接前先看一眼服务器是不是已经把它关了（读一下套接字，不等待）：关了就换新连接，下单请求不会发到一条已断的连接上、变成“结果未知”。
- 记录写库挪到下单请求发出之后（订单日志仍然先写，崩溃恢复不受影响），请求早几十微秒出门；订单日志写不进去时（例如磁盘满）仍然先等这张单的记录写进数据库、写不进就不发，和 Python 版一样。

**换回 Python 版 / 再换回来**（记录、网页保存的设置、暂停状态两边通用，同一个数据库文件）：

```bash
RT_IMPL=python bash deploy/gcp/rt.sh update   # 换成 Python 版（之后一直用它，直到再指定）
RT_IMPL=rust bash deploy/gcp/rt.sh update     # 换回 Rust 版
```

**编译**：虚拟机上用 Ubuntu 官方源里的 Rust 工具链（`rustc-1.97` / `cargo-1.97`，和别的 Ubuntu 软件包一样有签名），依赖按 `Cargo.lock` 锁定的版本编译，cargo 会逐个核对每个包的 SHA-256。第一次部署要多 3～5 分钟编译，以后 `update` 只编译改动的部分；编译完先跑全部离线测试，有一个失败就不换、原来的版本继续运行。

## 和 Railway 上的 huice 一起用（必看）

1. **Railway 上把 `RULE_TAKER` 改成 `off`**，再把这边改成 `on`。两边都开 `on` 时会在同一场一起抢、一起下单（同一个账户就是买双份，也会互相把对方的单当成卖单吃掉）。顺序：这边先用 `paper` 跑起来 → Railway 改 `off` 并重新部署 → 这边改 `on`。
2. **API Key 用一把专用的**（`RULE_API_KEY`）。Predict 按 Key 限流（每把有自己的每分钟额度：普通 240 次，高级的更多），两个进程用同一把 Key 会一起撞 429、一起停 20 秒。
   - 最好在 developers.predict.fun 再申请一把新的给这里用。
   - 如果把 Railway 上的 `RULE_API_KEY` 拿过来用，**要把 Railway 上的 `RULE_API_KEY` 删掉**（或者那边设 `RULE_KEY_LEND=off`）：Railway 上规则吃单关掉以后，那把 Key 会被一直借给盘口和预挂（`RULE_KEY_LEND`），这边再用就会撞限流。
   - 撞一次限流（429），这边**所有请求停 20 秒以上、期间不下新单**，赶上抢单时刻这一场就丢了。再申请一两把 Key 填进 `RULE_API_KEY_2`、`RULE_API_KEY_3` 当备用：在用的那把一被限流，同一个请求当场换下一把再发，不用停。自检（`/check`、`rt.sh check`）有一行“API Key 额度”：拿 Predict 回答里的额度（这一分钟这把 Key 一共用了多少）和这边自己发的次数比，多出来的就是别的程序在用这把 Key，会 ⚠️ 提示；最近一天被限流过几次也写在那里。
3. **账户：用同一个 Predict 账户，还是单独开一个？**
   - **同一个账户**（最省事，私钥和充值地址照抄）：
     - 赢的份额由 Railway 上的自动领取（`LIVE_AUTO_REDEEM=on`）一起领掉——这边不做领取。
     - Railway 的日亏损停机线（`LIVE_MAX_DAILY_LOSS_USD`）不再包含规则吃单的盈亏；这边用自己的 `RULE_MAX_DAILY_LOSS_USD` 管。
     - Railway 的持仓核对会看到“账户里有、记录里没有”的份额（规则吃单的成交）。黄金休市 4 档、黄金开盘第一档、原油开盘第一档这几场原策略和预挂本来就不做，没有影响；**黄金纽约 05:15**（以及默认关闭的 05:00、16:45、原油 00:45）原策略可能在开场后做同一场，Railway 有可能把这边的成交当成原策略某张订单的“📌 补记成交”记账——钱不会少，只是账记到了原策略名下。介意的话用单独账户，或者这边把 `RULE_GOLD_0515_CENTS` 设成 0。
     - 05:00、16:45、原油 00:45 这三条（默认关）如果在这边打开，Railway 上的预挂可能在同一场挂着另一边的买单，这边吃单时可能吃到自己的挂单（白付手续费）。
     - **预挂的买单在这边看就是卖单**：huice 的“发布即预挂”在新场次一发布就在涨、跌两边各挂 49¢ 的买单（`selfTradePrevention=CANCEL_TAKER`）。涨那边 49¢ 的买单，在跌的盘口上就是一张 51¢ 的卖单；这边的规则价是 58¢、60¢，会去买。同一个账户自己跟自己成交时，Predict 当场撤掉吃单的这一边，结果是“下了 N 份，没买到”，抢单记录里会写“Predict 当场就撤了这张单……不是我们撤的”（2026-11-23 起；之前的记录升级后也按同样的方法判断）。huice 1.150.1 / 1.151.1 / 1.154.19 起，预挂不再挂黄金、原油的休市场次、重开第一场和黄金纽约 05:15——这边默认开着的几条正好是这些场次；Railway 上跑的 huice 比这些版本旧时就可能出现，升级 huice 即可。
   - **单独账户**（在网站上另开一个账户、充 USDT、在网站上交易一次让授权生效）：两边互不干扰；但这边**不做自动领取**，赢的份额要定期到 predict.fun 网站上领取，否则 USDT 会越来越少。
4. **Telegram**：只发通知的话，可以直接用 Railway 那个机器人的 Token（发消息不冲突）。想在 Telegram 里用 `/status`、`/pause` 等命令，必须给这边**单独建一个机器人**（同一个 Token 只能有一个进程收消息）。

## 部署到 Google Cloud 东京（一步一步）

全程在浏览器里完成，不需要在自己电脑上装任何东西。

### 0. 准备

- 一个 Google 账号，打开 <https://console.cloud.google.com>。
- 第一次用要**开通结算**（绑定付款方式）：左上角菜单 → “结算”。
- 新建一个项目：顶部项目选择器 → “新建项目”，名字随意（例如 `ruletaker`），建好后选中它。

### 1. 打开 Cloud Shell

控制台右上角点 **“激活 Cloud Shell”**（`>_` 图标），底部会出现一个终端。它自带 `gcloud`，已经登录你的账号。确认项目：

```bash
gcloud config set project 你的项目ID
```

### 2. 取代码

```bash
git clone https://github.com/7CCCCC21X/Donglan.git
cd Donglan
git checkout claude/serene-shannon-ri6od9   # 合并到主分支之后可以省掉这一行
```

仓库是私有的：用户名填 GitHub 用户名，密码处粘贴一个 GitHub **Personal access token**（GitHub → Settings → Developer settings → Fine-grained tokens，给这个仓库 Contents 只读权限）。

### 3. 填设置

```bash
cp ruletaker.env.example ruletaker.env
nano ruletaker.env
```

至少填：`RULE_API_KEY`（或 `PREDICT_API_KEY`）、`PREDICT_PRIVATE_KEY`、`PREDICT_ACCOUNT`（用普通钱包就留空）。**先保持 `RULE_TAKER=paper`**。规则价格、份数可以照 Railway 上的值抄。`Ctrl+O` 回车保存，`Ctrl+X` 退出。

### 4. 一条命令部署

```bash
bash deploy/gcp/rt.sh deploy
```

它会：在 **asia-northeast1-b（东京）** 建一台虚拟机 `ruletaker`（`e2-standard-2`，Ubuntu 24.04，20 GB 盘）→ 上传代码 → 装 Ubuntu 官方源的 Rust 工具链、编译 → 跑全部离线测试（有一个失败就不启动）→ 把设置文件放到虚拟机的 `/etc/ruletaker/ruletaker.env`（权限 640）→ 用 systemd 启动并设成开机自启、崩溃自动重启。第一次大约 8～10 分钟（多数时间在编译）。第一次运行 `gcloud compute ssh` 会问是否生成 SSH 密钥，直接回车。

想换机器或区域：`MACHINE=n2-standard-2 ZONE=asia-northeast1-a bash deploy/gcp/rt.sh deploy`。

### 5. 自检

```bash
bash deploy/gcp/rt.sh check     # 登录、账户、余额、授权、这个区域能不能下单（只读）
bash deploy/gcp/rt.sh latency   # 到 Predict 的延迟（只读）
bash deploy/gcp/rt.sh status    # 状态，就是 huice 的 /rules
```

（设了 Telegram 命令机器人的话，也可以直接给它发 `/check`；`bash deploy/gcp/rt.sh test` 或 `/test` 再做一次真实的挂单测试。）

`check` 会向下单接口发一个**空订单**（内容为空，Predict 只会拒为“无效”，不可能成交）来看这个区域能不能交易：返回 400 是正常的，返回 403 说明这个区域不能下单，要换区域。**请自己确认 Predict.fun 的服务条款允许你在这个地区使用。**

### 6. 切到真实吃单

1. `paper` 跑一两天，`rt.sh status` 看“抢单记录”和每场的结果。
2. Railway 上 `RULE_TAKER=off`，重新部署。
3. 这边：`nano ruletaker.env` 把 `RULE_TAKER=on`，然后

```bash
bash deploy/gcp/rt.sh env
```

4. 部署完把 Cloud Shell 里的 `ruletaker.env` 删掉（里面有私钥，脚本也会提醒）：`shred -u ruletaker.env`。虚拟机上，私钥已经自动从设置文件收走、加密保存（见“[私钥加密保存](#私钥加密保存)”）。以后改设置用 `bash deploy/gcp/rt.sh edit`，换私钥用 `bash deploy/gcp/rt.sh key`；规则价格、份数这些直接在网页控制台里改更方便。
5. 运行一次安全加固：`bash deploy/gcp/rt.sh lockdown`（见“[安全](#安全)”）。

### 费用

`e2-standard-2` 东京按需价格大约每月 60 多美元（以控制台显示为准），加上 20 GB 磁盘一两美元。想省钱可以 `MACHINE=e2-medium`（共享核心，约一半价格，偶尔会有几毫秒的 CPU 抖动）。不用了就 `bash deploy/gcp/rt.sh delete`。

## 日常操作

都在 Cloud Shell 的仓库目录下运行：

| 命令 | 作用 |
|---|---|
| `bash deploy/gcp/rt.sh lockdown` | **安全加固**（部署后运行一次）：封掉这台机器所有入站连接，SSH 只走 Google 的 IAP 通道；`unlock` 解除。见“[安全](#安全)” |
| `bash deploy/gcp/rt.sh console` | 打开网页控制台和复盘页（见下一节） |
| `bash deploy/gcp/rt.sh status` | 状态（文字版）：模式、推送、账户余额、每秒检查时段、下一个抢单时刻、每条规则的下一场、抢单记录、今天的成交和盈亏 |
| `bash deploy/gcp/rt.sh check` | **自检**：登录、账户、余额、授权、下单接口在这个区域能不能用、读一次多快、推送、记录、场次，最后一句结论（和 Telegram `/check`、控制台“自检”按钮一样） |
| `bash deploy/gcp/rt.sh test` | **挂单测试**：挂一张约 $1、远低于市价的买单，查到后马上撤掉，每一步写 Predict 的回答和往返用时（和 Telegram `/test` 一样） |
| `bash deploy/gcp/rt.sh latency 4000` | 量这台机器到 Predict 的延迟（只读，约 1 分钟，别在抢单时段跑）：推送延迟、REST 和推送谁先看到新盘口、币安指数延迟、Key 的额度。4000 是只给这次测量用的每分钟请求数（不写就按设置里的 `PREDICT_RATE_PER_MIN`），服务不动 |
| `bash deploy/gcp/rt.sh logs` | 实时日志（`Ctrl+C` 退出） |
| `bash deploy/gcp/rt.sh pause` / `resume` | 暂停（不开新单，挂着的单当场撤）/ 恢复；暂停在重启后仍然有效。今日亏损停机后 `resume` 会从现在的盈亏起再给一个 `RULE_MAX_DAILY_LOSS_USD` |
| `bash deploy/gcp/rt.sh mode paper` | 运行中切换模式（off / paper / on），**不会高于**设置文件里的 `RULE_TAKER` |
| `bash deploy/gcp/rt.sh update` | 代码更新后：`git pull` 再运行它，重新上传、跑测试、重启（设置不动） |
| `bash deploy/gcp/rt.sh env` | 上传改好的 `ruletaker.env` 并重启 |
| `bash deploy/gcp/rt.sh edit` | 直接在虚拟机上改设置文件（nano，`Ctrl+O` 回车保存、`Ctrl+X` 退出），检查无误才重启——私钥不用留在 Cloud Shell。设置文件里**看不到私钥**（加密保存着）；照老习惯贴进去一行 `PREDICT_PRIVATE_KEY=…`，保存后也会被收进加密保存、从文件里删掉 |
| `bash deploy/gcp/rt.sh set 设置名 值` | **改一项设置，不用编辑器**（手机上也能用）：例 `rt.sh set RULE_WS_CONNECTIONS 3`。同名的行全部换掉（服务只认第一行），没有就加在最后；检查无误才重启，服务不认的值把设置文件恢复原样、照旧运行。不写值就隐藏输入，填 Key 用：`rt.sh set RULE_API_KEY_2`。值里不能有空格、引号、`#`；私钥不行（用 `rt.sh key`） |
| `bash deploy/gcp/rt.sh key` | **换私钥**：在 Cloud Shell 里粘贴（屏幕不显示、不进命令历史），先在链上核对它是不是 `PREDICT_ACCOUNT` 的控制钥匙，对了才在虚拟机上加密保存、重启服务；不对什么都不改 |
| `bash deploy/gcp/rt.sh audit` | 私钥安全体检（只读）：私钥是不是加密保存、明文还在不在任何文件里、权限、日志、加固、谁能登录（私钥本身不会显示） |
| `bash deploy/gcp/rt.sh restart` / `stop` / `start` | 重启 / 停止 / 启动服务 |
| `bash deploy/gcp/rt.sh ssh` | 登录虚拟机 |
| `bash deploy/gcp/rt.sh probe asia-southeast1-b` | 在别的区域临时开一台小机器量推送延迟和读盘口，量完自动删除（只带 API Key，从虚拟机读）；怎么比见“为什么是东京、怎么确认” |

**在手机上**：装 Google Cloud App（iOS / Android），App 里的 Cloud Shell（终端图标 `>_`）和电脑上的一样，`~/Donglan` 也在，上面这些命令照用；改设置用 `rt.sh set`（手机键盘没有 Ctrl 键，`rt.sh edit` 里的 nano 存不了盘）。**虚拟机页面上的“暂停 / 停止 / 重置 / 删除实例”是整台机器的操作，不是暂停吃单**——点了机器就停了（删除连记录一起没了）；暂停吃单用 Telegram `/pause` 或 `rt.sh pause`。

停止或重启时，服务会先等在途订单的应答（最多 25 秒）、撤掉还挂着的单，再退出。

### Telegram：怎么绑定（通知、命令、自检）

**最简单的绑法：给这个服务单独建一个机器人，通知和命令都走它。**

1. 在 Telegram 里找 **@BotFather**，发 `/newbot`，起个名字（例如“规则吃单东京”）和用户名（必须以 `bot` 结尾），它会回一串 Token（`123456:ABC…` 这样的）。
2. 点开新机器人的对话，按 **Start**（机器人不能主动给没和它说过话的人发消息）。
3. 设置文件里填三行（在虚拟机上直接改：`bash deploy/gcp/rt.sh edit`）：

   ```
   TELEGRAM_COMMAND_TOKEN=新机器人的 Token
   TELEGRAM_COMMANDS=on
   ADMIN_USER_ID=你的数字用户 ID
   ```

   用户 ID 就是 Railway 变量里那个 `ADMIN_USER_ID`，照抄。不知道的话：先只填前两行（`ADMIN_USER_ID` 留 0）保存，给新机器人发 `/id`，它回“你的用户 ID：…”（`/id` 谁发都回，别的命令只认 `ADMIN_USER_ID`），再 `rt.sh edit` 填上。
4. 编辑器里 `Ctrl+O` 回车保存、`Ctrl+X` 退出，它会先检查设置再重启。几秒后新机器人会发来“🚀 规则吃单已启动”，输入框旁边的“菜单”里有全部命令。发 `/check` 试一下。

这样启动、成交、结算、告警都发到你和新机器人的私聊里，和 Railway 机器人的消息分开。

**想让通知继续发到原来的群话题**（和 huice 的通知放一起）：再加两行——`TELEGRAM_BOT_TOKEN=Railway 那个机器人的 Token`（只用来发消息，和 Railway 不冲突）和 `TELEGRAM_CHAT_ID=群ID:话题ID`。群和话题的 ID 这样查：把新机器人拉进群，在那个话题里发 `/id@新机器人的用户名`，它回“这个聊天：-100…:话题ID”，照抄。命令仍然发给新机器人。

**不要这样填**：把 Railway 机器人的 Token 填进 `TELEGRAM_COMMAND_TOKEN`，或者在 `TELEGRAM_COMMANDS=on` 时只填 Railway 的 `TELEGRAM_BOT_TOKEN`——同一个 Token 只能有一个程序收消息，两边会互相抢，命令都收不全。

**机器人没反应时**：运行 `bash deploy/gcp/rt.sh check`，看 **Telegram 那一行**，它直接说原因和怎么改——`TELEGRAM_COMMANDS` 不是 on（只发通知、不收命令）、Token 不对、这个机器人被别的程序占着（同一个 Token 有别的程序在收消息，或设了 webhook）、`ADMIN_USER_ID` 没填或填错（“用户 X 发过 /status，但 ADMIN_USER_ID 是 Y”）、通知发不出去（还没在机器人对话里按 Start）。这些也会写进日志（`rt.sh logs`）。不是管理员的人私聊机器人发命令，机器人会回他的用户 ID——`ADMIN_USER_ID` 填错时你自己一发就知道该填什么。

| 命令 | 作用 |
|---|---|
| `/menu`（或 `/start`） | **按钮菜单**：一张卡片，上面是现在的模式、暂停与否、今天已结算的盈亏和可用余额，下面是按钮——📊 状态、🔎 自检、⏸ 暂停、▶️ 恢复、关 / 只记录 / 真实吃单（现在的打 ✅）、🧪 挂单测试、🔄 刷新。会开始真实下单的三个（恢复、切到真实吃单、挂单测试）先问一句“确定吗”，60 秒内点“确定”才执行，过时的确认不算；只认 `ADMIN_USER_ID` 点的。点完结果另发一条消息，卡片自动更新成最新状态 |
| `/settings` | **设置**：一张卡片，每个设置一个按钮（显示现在的值）；点一项看说明，再点一个预设值当场生效（和网页控制台保存一样：整体校验、写进数据库、重启后仍有效），“恢复设置文件的值”回到部署设置。按钮只认这一项自己的预设值。别的数值发 `/set 设置名 数值`（例：`/set RULE_MAX_DAILY_LOSS_USD 30`），`/reset 设置名` 回到设置文件的值 |
| `/review`（`/review 7`、`/review all`） | **复盘**：真实和只记录各买了几场、花了多少、赢几场输几场、盈亏和收益率；按规则；最近几天每天的盈亏和累计；最近几场。抢单那几秒不算，给 30 秒内算好的 |
| `/check` | **自检**（huice `/live check` 的对应物，内容更多）：模式和停机线、Predict 登录、Predict 账户的控制钥匙（链上核对）、USDT 和 BNB 余额（够不够买满一场）、交易所授权、**下单接口在这个区域能不能用**（发一个空订单，Predict 拒为无效 = 能用，403 = 这个区域不能交易，空订单不可能成交）、读一次 Predict 的往返、推送连接和推送延迟、币安指数（盘中吃单开着时）、数据库和订单日志、接下来一天的场次和市场找到没有、最近问题，最后一句结论 |
| `/test` | **挂单测试**（huice `/live test` 的对应物）：在一个撮合已开启的规则场次（没有的话用 BTC 当前的 15 分钟场次）挂一张买涨的限价单——最高 2¢、低于最高买价 1¢、**绝不高于最低卖价**（不会成交），约 $1，10 分钟后自动过期；按哈希查到它、撤掉、再查最终状态，每一步写 Predict 的回答和往返用时。签名、授权、这个区域能不能下单一次验证完。它不算规则吃单的单，不进记录。**它也是真实的单**：`LIVE_TRADING_ALLOWED` 关着、已暂停、服务正在停止时一律不做，请求真正发出前（要新建连接的话握手之后）再核一次；想测又不想让它自动吃单：先 `/mode paper`，再 `/resume`，再 `/test`。下单的应答丢了（超时、5xx）不会说“没下成”：按哈希查，查到就照样撤掉；查不到报“结果未知”，它 10 分钟后自己过期。撤掉前成交了几份的话照常结算；最后一次查询没读到时，成交按前面查到的记，结论提示到 Predict 核对 |
| `/speed`（`/speed 4000`） | **测速**（菜单上的“📶 测速”，只读、不下单，约 1 分钟）：和 `rt.sh latency` 同一套测量，在服务里跑完把结果发回来——推送延迟、REST 和推送谁先看到新盘口（最后一行给结论）、币安指数延迟、Key 的额度，再加上服务自己的推送连接：开了几条、各自先到几次、后到的晚多少。`/speed 4000` 是只给这次测量用的每分钟请求数（REST 约每 60 ms 读一次），设置不动。抢单时段和它前 3 分钟不测（会占这把 Key 四分之一的额度），同一时间只测一次 |
| `/status`（或 `/rules`） | 状态，和 huice 的 `/rules` 同一个版式：模式、每秒检查时段、下单速度、网络、每条规则的下一场和近 30 天的盘口观察、抢单记录（每场卖单几点几秒出现、多久被吃光、我们的单每一段用了多久）、今天的成交和盈亏。比 huice 多一行账户余额；没有“优先”和“借 Key”那两段（这里只有规则吃单）。一般一条消息发完，超过 Telegram 的字数上限时按行分成两条 |
| `/pause`、`/resume` | 暂停（挂着的单当场撤）/ 恢复 |
| `/mode off\|paper\|on` | 切换模式，不高于设置文件的 `RULE_TAKER` |
| `/id` | 查你的用户 ID 和这个聊天的 ID（任何人都能用） |

只认 `ADMIN_USER_ID` 发来的命令（`/id` 除外），别人发了不理。自检、挂单测试要几秒，机器人先回“自检中…”，结果随后发来。

## 控制台和复盘页

一个网页，两个标签：**控制台**和**复盘**。网页在虚拟机上只对本机开放（`127.0.0.1:8080`），不开任何公网端口；从浏览器看要走一条 SSH 通道：

1. 在 Cloud Shell 里运行 `bash deploy/gcp/rt.sh console`（窗口保持开着），**等它显示“✅ 通道已接通”**——加固后走 Google 的 IAP 通道，要几秒到十几秒。在这之前点预览会看到“Unable to forward your request to a backend / Couldn't connect to a server on port 8080”，等接通后刷新那一页就好。
2. 点 Cloud Shell 工具栏右上角的 **「网页预览」**（Web preview，方框里一个眼睛的图标）→ **「在端口 8080 上预览」**。浏览器新开一页就是控制台。这个预览地址只有登录了你的 Google 账号才能打开。
3. 看完回到 Cloud Shell 按 `Ctrl+C` 关掉通道。

**为什么会“打不开”**：这个网页跟着 Cloud Shell 走——通道开在 Cloud Shell 里，Cloud Shell 闲置一段时间会被 Google 收回，通道也就没了（这是 Cloud Shell 本身的规矩，改不了）。`rt.sh console` 在 Cloud Shell 还在的时候，通道断了会自动重连（“已重新接通，刷新网页就好”）；Cloud Shell 被收回之后回来再运行一次这个命令。**随时都能用的是 Telegram 机器人**：`/menu` 里有状态、暂停 / 恢复、切模式、⚙️ 设置（点一项换一个值）、📈 复盘，手机上也一样，不用开 Cloud Shell。图表和导出 CSV 才需要这个网页。

通道开着时这个 Cloud Shell 标签页被占用，要运行别的命令点终端标签旁边的 **+** 开一个新的。Cloud Shell 端口 8080 被占用时换一个：`bash deploy/gcp/rt.sh console 8081`，预览时选“更改端口”填 8081。

用自己电脑上的 gcloud 也可以（不受 Cloud Shell 超时影响）：`gcloud compute ssh ruletaker --zone asia-northeast1-b --tunnel-through-iap -- -N -L 8080:127.0.0.1:8080`，然后打开 <http://localhost:8080>（运行过 `rt.sh lockdown` 就必须带 `--tunnel-through-iap`；没加固时可以去掉）。设了 `STATUS_KEY` 时网页会先要口令（存在这个浏览器里）。

**控制台**（每 3 秒刷新）：

- 现在：模式、现在下不下单和原因（暂停、未就绪、日亏损停机、限流、余额……）、账户 USDT（可用余额扣掉了在途订单）、今天已花和已结算盈亏、推送是否连着和推送延迟、每秒检查是否在进行。
- 操作：模式 关 / 只记录 / 真实吃单（**不能高于设置文件的 `RULE_TAKER`**，切到真实吃单要确认）、暂停 / 恢复（暂停时挂着的单当场撤掉；亏损停机后点恢复会从当时的盈亏起再给一个额度）、撤掉全部挂单。
- 每条规则的下一场：价格、下一场的北京时间、对手挂单时刻、它最近一次看盘说了什么（还没发布 / 盘口没有 ≤58¢ 的涨 / 等撮合开启 / 已下单 …）。
- 速度与网络：服务所在区域、主循环延迟、到 Predict 新建连接和读一次的用时、近 30 天真实订单“盘口变化→推送到达→发出→应答”各段中位和最快、预先签好的单用上了几张。
- **设置**：和 huice 控制台“规则吃单”一组一样——黄金 / 原油的开关、每场份数、每条规则的盘前价和盘中价、每天上限、今日亏损停机线、每秒检查时段、对手提前多少分钟。点预设值**立即生效**，也可以填自定义值保存；保存时和启动时一样整体校验，填错了什么都不改并说明原因。保存**当场生效**，保存途中你切换的模式（比如刚改成只记录）不会被这次保存改回去；数据库一时写不进去（被锁住、磁盘满）时页面明说“已经生效，但还没写进数据库”、不显示“已保存”，写完之前重启会回到改之前的值，数据库恢复后自动补写（暂停、恢复、切换模式也一样会说明）。网页保存的值重启后仍然有效，标着“网页保存”，点“恢复部署设置”回到设置文件里的值（接口：`{"reset":["字段名", …]}` 恢复这几项，`{"reset":"all"}` 全部恢复；写错格式一律拒绝，不会被当成“全部恢复”）；设置文件后来改了、和网页保存的值冲突时，启动时只删掉冲突的那一项并在 Telegram 告诉你。私钥、Key、链、模式上限这些不能在网页上改。
- 最近问题：最近 12 条读取失败、下单被拒等。

**复盘**（时间范围：近 7 天 / 30 天 / 90 天 / 全部，按场次开场时间算）：

- 真实吃单、只记录各一张总账：已结算盈亏、回报率、赢 / 输场数、买到的份数和成本、待结算。
- 累计盈亏曲线（实线真实、虚线只记录）。
- 按规则：每条规则真实 / 只记录分开的场次、份数、每份成本、盈亏、赢 / 输；其中盘中买的单列一张。
- 盘口观察：每条规则看了几场、几场有规则价以内的卖单、平均可买份数、最低卖价中位、撮合开启和卖单出现在开场前多久、没买到就没了的场次（卖单存活多久）。
- 抢单记录：每一场卖单几点几秒出现（毫秒）、多久开始被吃、多久被吃光、我们买到多少、每张单出现后几毫秒发出、推送延迟、自己用了多久、是不是预先签好的、往返多久。“出现后几毫秒发出”只算卖单刚出现（1 秒内的盘口）就发的单；隔了很久、跟着后来的盘口发的单（卖单没了又出现、等撮合开启等了几小时）写成“首次出现 19 小时后才发出（跟的是后来的盘口）”，也不算进“我们的单在出现后 中位 … ms 发出”——那一句只跟最快的对手比反应速度。
- 按日期：每天的场次、赢 / 输、成本、当日盈亏、累计。
- 最近的场次：每场买了多少、均价、结果、盈亏。
- **导出 CSV**：所有订单一行一条（真实和只记录都有），Excel 直接打开。

复盘数据算一次只要几毫秒，留 30 秒；抢单时刻前后那几秒不算（给的是上一次的），不会挡住下单。

## 提速：具体改了什么

规则吃单拼的是“对手在整刻钟后几秒挂出一排卖单，谁先吃到算谁的”。huice 11-18 的记录：卖单出现后 0.35–0.42 秒被别人吃光；我们的单在出现后 289 ms 发出（推送 178 ms + 机器人自己 111 ms），再加半个往返约 150 ms 才到 Predict。这里每一段都缩短了：

| 环节 | huice（Railway 阿姆斯特丹，共用一个进程） | 本服务（东京，独立进程） |
|---|---|---|
| 盘口变化 → 推送到达 | 中位 178–246 ms | 东京就近接收；部署后 `status` 的“推送延迟中位”就是它 |
| 推送到达 → 请求发出 | 最快 1 ms，但常被主循环占住（111 ms、2098 ms、2540 ms） | Rust 版本机测 0.07 ms（预先签好）/ 0.12 ms（当场签名）；没有别的任务和它抢 |
| 请求 → Predict（半个往返） | 约 150–180 ms（读一次 233–311 ms） | `rt.sh latency` 量；`status` 的“网络”一行持续显示 |

具体做法：

1. **只做规则吃单的独立进程**：没有原策略的整步、预挂的几万条记录和账户快照、复盘页重算、σ 校准，主循环延迟只剩零点几毫秒（`status` 的“速度”一行实时显示）。
2. **推送一到，当场看这一场**：每一场有自己的“正在看”标记，读推送的那个任务直接调用这一场的判断、定份数、签名，并当场把下单请求的字节写进到 Predict 的连接，然后才去读下一帧（不经过调度、也不受调度器的轮转预算限制）。另一场在等 REST 读取，不再挡住这一场（huice 同一时刻只能跑一轮）。
3. **预先签好单**：每秒检查时段和对手挂单时刻（`RULE_LEAD_MINUTES`）前后，每场“这一场还能买的全部份数、按规则价”的那张单提前签好。salt 由场次和第几张单决定，所以预先签的和当场签的是**同一张单**，用上时 `status` 的抢单记录写“预先签好”。
4. **不等上一张的应答**：一张单发出后马上可以看下一次推送；盘口上新出现、超出在途订单份数的卖单立刻另下一张（每场最多 3 张同时在途，份数上限照算在途的）。
5. **连接保温**：忙的时段（开场前 15 分钟、对手挂单时刻、每秒检查时段、盘中）保证 2 秒内用过一条到 Predict 的连接——下单请求只复用 3 秒内用过的连接（否则怕连接已被服务器关掉、订单结果不明），这样下单永远不用重新 TCP+TLS 握手。
6. **下单路上不读链**：交易所授权额度是无限额度时不再在下单前读链（后台每小时核对），登录 token 在后台提前续期，余额在后台读（忙的时段每 20 秒、平时每 2 分钟、每次成交后马上读一次）。
7. **订单不排在读取后面**：下单、撤单有自己的并发名额（读取最多占 4 个，至少留 2 个给订单），限流节拍里订单可以预支，读取慢的时候订单不排队。
8. **更快的编码和签名**：Rust 原生 JSON 解析和 secp256k1 签名（带预计算表，启动时就建好）；订单请求体直接按字段拼成字节；EIP-712 哈希按字段直接拼——和 Python 版、和 eth-account 的通用编码器逐字节一致（测试里核对）。
9. **没有垃圾回收停顿**：Rust 没有垃圾回收（Python 版要在抢单那几秒手动关掉它）；连接复用前先确认服务器没关它，下单请求不会落在一条已断的连接上。
10. **部署在东京**，systemd 里给进程 `Nice=-5`。

**控制台、复盘、Telegram 会不会拖慢抢单**：它们和下单在同一个线程上轮流跑，一件事算的时候，刚到的推送要等它算完。实测（Rust 版，记录里 600 场，`cargo test --release bench_side_tasks -- --ignored --nocapture`）：

| 什么 | 占线程多久 | 抢单那几秒 |
|---|---|---|
| 控制台页面刷新（开着时每 3 秒一次） | 中位 0.3 ms，最慢 0.8 ms | 照常（影响不到 1 ms） |
| Telegram 推送消息（成交、结算） | 几微秒（发送是网络等待，不占线程） | 照常 |
| `/status`、`rt.sh status` 的状态文字 | 中位 3.5 ms，最慢约 10 ms | **等抢单那几秒过去再算**（最多等 30 秒） |
| 导出 CSV | 约 2 ms | 等抢单那几秒过去再导出 |
| 复盘计算 | 11–18 ms | 不算（30 秒内用缓存，抢单那几秒给缓存的） |

“抢单那几秒”：对手挂单时刻前 1 秒到后 15 秒、盘中开始后的前 12 秒、盘口已有卖单在等撮合开启的时候（只在真实吃单模式）。`/check` 和 `/test` 要访问 Predict：下单有自己保留的并发名额、限流节拍里可以预支，不排在它们后面；但 `/test` 本身是一张真实的单，别在抢单那几分钟做。

没有改的：规则本身、价格、份数、每天上限、开场前 15 秒停止下单、签名在开场前 5 秒到期（最后 2 分钟里除外，见下）、1.5 秒后撤掉没成交的部分、60 秒确认没有晚到的成交、409 / 应答丢失按哈希核对绝不重发、手续费按份数扣——全部和 huice 一样。

## 换了更高级别的 API Key 之后

额度大了，机器人不会自己知道，要做三件事：

1. **告诉它新的额度**：`bash deploy/gcp/rt.sh edit`，把 `PREDICT_RATE_PER_MIN` 改成新额度的九成（不知道额度是多少：先跑第 2 步，看“接口限额”那一行；没写的话问 Predict）。
2. **量一下 REST 和推送谁先看到新盘口**：Telegram 发 `/speed 4000`（或菜单里的“📶 测速”），或者 `bash deploy/gcp/rt.sh latency 4000`（别在抢单时段跑；4000 是只给这次测量用的每分钟请求数，它会用掉四分之一左右，大约 1 分钟，设置文件和服务都不动；不写就按设置里的 `PREDICT_RATE_PER_MIN`）。REST 读的间隔就是按这四分之一算的：还是 220 时每 1.09 秒才读一次——读得这么稀，推送自然多半先到，比不出谁更新，这时它会直接说“太稀”而不下结论（2026-11-23 之前的版本会误判成“不比推送新”）。看这几行：
   - “REST 读盘口 … 新盘口从 Predict 时间戳到这里 最快 X ms”，和后面推送的“最快 Y ms”比；
   - “同一份盘口两边都看到 N 次：REST 先到 … 推送先到 …”；
   - 最后一行箭头给出结论。
3. **只有结论是“REST 的盘口比推送新”**，才把 `RULE_VERIFY_MS` 调小（比如 100）：对手挂单时刻前后 REST 读得更勤，有机会比推送早几十毫秒看到卖单。结论是“不比推送新”就不用动，读得再勤也没用。

### 推送延迟怎么压

“盘口变化→推送到达”（东京中位 60 ms 上下，最快 13 ms）几乎都花在 Predict 自己那边——从盘口变化到推送发出来；网络只占几毫秒，这边收到后处理不到 1 毫秒。Predict 那一段改不了，这边能做的只有两件，前提都是**这把 Key 不和别的程序共用**（见“和 Railway 上的 huice 一起用”第 2 条）：

1. **多开推送连接**：`RULE_WS_CONNECTIONS=3`（`rt.sh edit`）。三条连接各自订阅，同一份盘口谁先送到用谁的。有没有用看状态“速度”那一行：`推送 3 条连接：各自先到 a/b/c 次，同一份盘口后到的比先到的晚 中位 X ms`——X 就是多开连接省下的时间；X 只有零点几毫秒说明三条一样快，开不开都行。
2. **抢单那几秒用 REST 补位**：先量一次 `bash deploy/gcp/rt.sh latency 4000`（4000 是只给这次测量用的每分钟请求数，REST 约每 60 ms 读一次；设置文件和服务都不动）；结论是“REST 的盘口比推送新”，就把 `RULE_VERIFY_MS` 设成 50（这时 `PREDICT_RATE_PER_MIN` 也要调到额度的九成，不然读不了这么快）：对手挂单时刻前 10 秒到后 2 分钟，每 50 ms 读一次那一场的盘口，推送和 REST 谁先看到卖单就按谁下单。

再快也只能追到几十毫秒：对手里最快的人在卖单出现后 10 ms 左右就下手。要从根上不比这个速度，只能换打法——开场前先把买单挂好等着（还在试）。

另外两处会显示得更细：

- **状态里每张单的往返拆开了**：`往返 82 ms［排队 0 ms、复用连接、写出→应答 80 ms］`。排队是等额度和空位，连接是复用还是新建（新建会写握手用了多久），写出→应答是请求发完到 Predict 回话。抢单那一刻的往返比平时长，看这里就知道长在哪一段。
- **`/check` 会看 Predict 有没有给这些市场设吃单延迟**（speedBump 之类）：有的话，吃单的单在 Predict 那边要等这么久才撮合，抢单拼的就不只是网络了。

## 为什么是东京、怎么确认

huice 11-18 的网络一行：阿姆斯特丹到 Predict 的入口（Cloudflare）新建连接 7–31 ms，读一次盘口 233–311 ms。入口近、请求慢，说明 Predict 的服务器离欧洲很远，这个数和到东亚的往返吻合。

东京实测（11-20 那场 18:15）：读一次 12 ms、下单往返 49 ms、推送延迟中位 66–85 ms。

**抢单比的是哪一段**：卖单出现 → Predict 推送到我们（东京 66–85 ms）→ 发出（0 ms：预先签好，推送一到当场发）→ 半个下单往返（约 25 ms）到 Predict。对手在卖单出现后 10–50 ms 就到了。我们这头的处理已经是 0 ms，再省只能省网络：离 Predict 更近，推送和下单都短。所以先量清楚哪个区域最近。

量法（各区域请在**同一时段**量，比如同一个小时内；每个约 4～5 分钟，临时机器几美分；只带 API Key，从虚拟机的设置文件读，不带私钥）：

```bash
bash deploy/gcp/rt.sh latency                    # 正在跑的这台（东京），作为基准
bash deploy/gcp/rt.sh probe asia-southeast1-b    # 新加坡：临时开一台小机器，量完自动删掉
bash deploy/gcp/rt.sh probe asia-east2-a         # 香港
bash deploy/gcp/rt.sh probe asia-east1-b         # 台湾
bash deploy/gcp/rt.sh probe asia-northeast3-a    # 首尔
```

每次会看 BTC 15 分钟盘口 45 秒，量每一次盘口变化从 Predict 自己的时间戳到这台机器收到用了多久；同时量币安 XAUUSDT 指数（盘中规则用的就是它）每秒一次的推送延迟。临时机器和正式那台同一规格（`e2-standard-2`），比的是同样的机器。

- **主要比“推送延迟 … 中位”**：最小的区域离 Predict 的盘口最近，差 15 ms 以上才算数（同一区域前后两次也会差几毫秒）。
- **开着盘中规则的，再看“币安指数推送延迟”**：换到 Predict 更近的区域，币安可能变远，盘前快了、盘中可能慢，两项一起比。连不上币安的区域做不了盘中规则。
- “读盘口”只作参考，它代表不了下单：东京读一次 12 ms，下单往返却要 49 ms。

**真要换区域之前，再量下单往返**（只有用私钥才量得到）：在候选区域另起一台临时机器，只记录、不吃单，做一次挂单测试，看每一步的往返：

```bash
# 设置文件 ruletaker.env 用正式的那份改两处：RULE_TAKER=paper；删掉 Telegram 那几行（同一个机器人不能两台同时收命令）
VM=ruletaker-try ZONE=asia-southeast1-b bash deploy/gcp/rt.sh deploy
VM=ruletaker-try ZONE=asia-southeast1-b bash deploy/gcp/rt.sh test     # 和东京的 bash deploy/gcp/rt.sh test 比
VM=ruletaker-try ZONE=asia-southeast1-b bash deploy/gcp/rt.sh delete
shred -u ruletaker.env
```

两台不要同时开真实吃单（会互相抢同一场）。下单往返也明显更短，再把正式那台换过去。

**换更贵的机器、调内核参数有没有用**：几乎没有。实测推送一到就发单，处理只要 0.07～0.13 ms，主循环延迟中位 1.4 ms、最长 2 ms，CPU 不是瓶颈；时间全在网络上（推送 66–85 ms、下单半个往返约 25–41 ms）。

- c3 / c4 独享核：最多再省零点几毫秒。而且这两种要求 gVNIC 网卡（c4 还要 Hyperdisk），现在这台不能直接改规格，得重建。
- 绑核、`nohz_full`、`Nice`、`TimerSlackNS`：省的是微秒；改 GRUB 启动参数一旦写错，机器可能起不来。
- `TCP_QUICKACK`、`initcwnd`、`tcp_slow_start_after_idle`、BBR：管的是“我们往外发大量数据”时的确认和窗口。我们的单是一个小包、等一个回复，推送的发送窗口由 Predict / Cloudflare 那边决定，改我们这边不起作用；改默认路由改错了，机器会断网。
- 对时：GCP 上的 Ubuntu 默认就用 Google 自己的时间服务器（`metadata.google.internal`），`chronyc sources` 可以看到，误差在毫秒以内。

**AWS 还是 Google Cloud？** 对速度起作用的是机器在哪个城市，不是哪家云：两家在东京都有机房，请求都是先到 Cloudflare 的东京入口、再到 Predict。估计两家只差一两毫秒（没有实测过），而从阿姆斯特丹搬到东京省的是几百毫秒。这个仓库的部署脚本是给 Google Cloud 写的（Cloud Shell 一条命令部署、用网页预览看控制台，自己电脑上什么都不用装）；代码本身不挑云，`deploy/gcp/vm-setup.sh` 在任何 Ubuntu 24.04 机器上都能装。建议先在 Google Cloud 东京跑起来看实测；想和 AWS 东京（`ap-northeast-1`）比，在那边开一台小机器跑同一个 `ruletaker latency`（或 Python 版的 `python -m ruletaker latency`），比“读盘口”的中位数。如果别的区域明显更小，`ZONE=那个区域 bash deploy/gcp/rt.sh deploy` 换过去（先 `delete` 旧的，或者用 `VM=ruletaker2` 另起一台再删旧的，注意不要两台同时 `on`）。

- **怎么吃**：每场在 Predict 发布前后找到市场（发布约在开场前 24 小时），订阅它的盘口推送；盘口上规则方向有价格不高于规则价的卖单，就下一张限价单：价格 = 规则价；卖单 ≥20 份且不少于这一场还能买的 1/4（对手挂单时刻前后只要 ≥20 份）时，份数 = 这一场还能买的全部份数（它吃到的是到达那一刻盘口上的全部），否则按看到的份数；每场最多 `RULE_*_SHARES` 份，每天最多 `RULE_MAX_DAY_USD`，不超过账户 USDT。不是 post-only，1.5 秒后撤掉没成交的部分，60 秒后确认最终成交。开场前 15 秒起不再下单，签名在开场前 5 秒到期。**开场前最后 2 分钟里下的单例外**：Predict 不收 2 分钟内就到期的单（报错 `expiry is too soon (minimum 2 minutes from now)`，11-24 18:15 那张就是这样没下成），这段时间的单签到开场后 1 分 55 秒到期（离最晚能发单的开场前 15 秒正好 2 分 10 秒），没成交的部分照旧 1.5 秒后撤掉；盘中最后 2 分钟同样签到这一场结束后 1 分 55 秒。撮合还没开启时（只收 post-only 挂单）每 0.3 秒左右读一次状态，开启那一刻就买。被拒后这一场 30 秒后再试，拒满 5 次不再下。
- **每秒检查时段**（`RULE_FAST_HOURS`，默认北京 01:00–07:00）和**对手挂单时刻**（`RULE_LEAD_MINUTES`，默认开场前 300 分钟）：每秒看一次、每秒最多 3 次 REST 核对推送有没有漏、提前 1 分钟准备好登录和授权、预先签好单。
- **盘中吃单**（`RULE_GOLD_SHUT_LIVE_CENTS`、`RULE_GOLD_OPEN_LIVE_CENTS`，默认 0 = 不做）：黄金休市 4 档和开盘第一档在开场后接着买，条件是币安 XAUUSDT 合约指数已经站在规则方向（休市 4 档比起点高 0.005% 以上、开盘第一档低 0.02% 以上，起点取起点那根 1 分钟指数 K 的收盘和 Predict 页面的起点价里对规则方向更不利的那个）；开场 3 秒后开始、结束前 15 秒停止，第 1 分钟最高按盘前价格，指数一推到就当场看。需要这台机器能连币安合约行情（`fapi.binance.com`、`fstream.binance.com`），连不上时状态页会写，盘中就不买。

| `CME_EARLY_DAYS` / `CME_CLOSED_DAYS` | 内置到 2027-12-24 | CME 节假日（提前收市 / 全天休市），格式 `2026-12-24,2026-12-31`。日历最后一天前 30 天起，自检、状态页和 Telegram（每天一次）提醒补上之后的日子；过了最后一天**不再真实下单**（之后哪天休市不知道，错过一天就会在不动的指数上下单），补上后重启恢复 |
| `STATE_DB` | 虚拟机上 `/var/lib/ruletaker/ruletaker.sqlite3` | 记录数据库 |

## 安全

**先说实话**：服务要自动下单，就必须用得到私钥，所以私钥一定在那台机器上，“服务器上的私钥绝对安全”做不到。能做的是两件事：让能碰到它的路尽量少；万一被拿走，损失有上限。

### 私钥放在哪、谁能拿到

| 位置 | 保护 |
|---|---|
| Cloud Shell 里的 `ruletaker.env`（第一次部署时） | Cloud Shell 的个人磁盘，只有你的 Google 账号进得去；部署完删掉（`shred -u ruletaker.env`，脚本会提醒）。以后换私钥用 `rt.sh key`，不用再写进文件 |
| 传到虚拟机的路上 | SSH 加密通道 |
| 虚拟机上的设置文件 `/etc/ruletaker/ruletaker.env` | **没有私钥**：部署时自动收走，原来那行换成一句说明；文件原来的内容被覆盖掉 |
| 虚拟机上的 `/etc/credstore.encrypted/predict_private_key` | **加密的**：用这台机器自己的密钥加这台机器的虚拟 TPM 封起来，只有 root 能读这个文件，拷到别的机器上解不开；磁盘本身也由 Google 默认加密 |
| 服务运行时 | systemd 替服务解开，放在只属于这个服务的内存目录里（只有服务自己的用户能读，不进磁盘、不进交换分区，服务停了就没）；专用的、不能登录的用户运行；不写 core dump |

**不会出现在**：GitHub（`.gitignore` 排除了 `ruletaker.env`）、虚拟机的设置文件（`rt.sh edit` 打开看不到）、日志（只写“有没有设置”；程序里的配置对象打印出来也只显示“有没有设置”，测试里核对过）、服务进程的环境变量和命令行、网页控制台（看不到也改不了）、Telegram 消息、虚拟机的元数据、测延迟用的临时机器（`rt.sh probe` 只带 API Key 过去）。

**谁能拿到**：能登录你 Google 账号的人（能 SSH 进机器、能读磁盘），和能往这个 GitHub 仓库推代码的人（`rt.sh update` 会把仓库里的代码装到机器上运行）。真正的锁是这两个账号。

### 私钥加密保存

**打开设置文件看不到私钥**：`rt.sh update` / `deploy` / `env` 时，虚拟机上的 `vm-key.sh` 把设置文件里的 `PREDICT_PRIVATE_KEY` 收走：

1. 用 systemd 自带的 `systemd-creds` 加密，封进这台机器自己的密钥（`/var/lib/systemd/credential.secret`，只有 root 能读）和这台机器的**虚拟 TPM**（Shielded VM 自带）；存成 `/etc/credstore.encrypted/predict_private_key`（root 专属、权限 600）。
2. **先证明能用才动手**：让 systemd 按服务启动时的方式（服务的用户、服务的设备限制）把它解开，交给程序算出签名地址，和原来那把的地址对上了，才换。对不上、或这台机器没有 TPM 能用，就退回只用本机密钥；再不行就什么都不改，私钥照旧在设置文件里、服务照常跑，并说明原因。
3. 设置文件里所有写着私钥的行（包括注释掉的旧行）删掉，换成一句说明；文件原来的内容被覆盖，不是只改个名字。
4. 服务启动时，systemd 替它解开，放进只属于这个服务的内存目录；程序从那里读，不经过设置文件、环境变量和命令行。

**换私钥**：`bash deploy/gcp/rt.sh key`，在 Cloud Shell 里粘贴（不显示、不进命令历史、不写进任何文件），经 SSH 通道传过去；先在链上核对它是不是 `PREDICT_ACCOUNT` 的控制钥匙，对了才加密保存、删掉设置文件里的旧私钥、重启服务。照老习惯用 `rt.sh edit` 把私钥贴进设置文件也行，保存后一样会被收进加密保存。Telegram `/check`、`rt.sh check` 会写“私钥：加密保存在这台机器上”；还在设置文件里是明文的话写 ⚠️ 并告诉你怎么改。

**它防住的**：截图、录屏、旁人看到屏幕（`rt.sh edit` 打开的文件里没有私钥）；设置文件被复制、备份、误发出去；磁盘快照或磁盘被拷到别的机器上（用上了 TPM 时，没有这台机器的 TPM 解不开；用的是哪种，`rt.sh update` 和 `rt.sh audit` 都会写）。

**它防不住的**（实话）：已经拿到这台机器 root 的人。服务要自己下单，就得在运行时用到私钥，root 能做服务能做的一切。所以真正的锁仍然是你的 Google 账号（见下面“需要你自己做的”），以及钱包里只放够用的钱。

**要知道的**：私钥和这台虚拟机绑在一起。删掉重建虚拟机、从快照另起一台，都解不开原来那份：用新的设置文件 `rt.sh deploy` / `env`，或者 `rt.sh key` 再设一次。万一服务因为解不开私钥起不来，`rt.sh status` 会直接说，照提示 `rt.sh key` 重设即可。改成加密保存之前拍过的磁盘快照里，还是旧的明文设置文件：拍过就删掉（没拍过不用管）。

### 脚本已经替你做的

- 机器**不带服务账号**：就算有人进了机器，也拿不到能操作你 Google Cloud 项目的令牌。
- 服务只往外连（Predict、BNB 链节点、币安、Telegram），**不监听任何公网端口**；控制台只在本机 `127.0.0.1`，要看得走 SSH 通道。
- 2026-11-19 之前部署的机器带着项目默认的服务账号（`rt.sh audit` 会提示）：`bash deploy/gcp/rt.sh nosa` 去掉它（要停机约 1 分钟，会先问；服务随机器自动重新启动）。
- **`bash deploy/gcp/rt.sh lockdown`**（部署后运行一次）：防火墙封掉这台机器的所有入站连接，SSH 只能走 Google 的 IAP 通道——连接先过 Google 登录和项目权限检查，公网上连不到它的 22 端口。脚本先验证通道能用才封；封完验证失败会自动撤回。之后 `rt.sh` 的所有命令自动走通道（慢一两秒）；`rt.sh unlock` 解除。
- **依赖锁定并校验哈希**：Rust 版的每个依赖包按 `Cargo.lock` 锁定版本，cargo 下载时逐个核对 SHA-256（`--locked`：锁文件和代码对不上就拒绝编译）；编译器来自 Ubuntu 官方源（有签名的软件包，不从网上下载安装脚本）。Python 版（备用）的每个包按 `python/requirements.lock` 的 SHA-256 校验，只装现成的 wheel。
- Shielded VM（安全启动、vTPM、完整性监控）；Ubuntu 默认自动装安全更新。
- 网页控制台的所有修改操作要专用请求头（别的网站的页面发不出来）；私钥、Key 不能在网页或 Telegram 里改；Telegram 只认 `ADMIN_USER_ID`，而且改不了价格和份数。

**随时体检**：`bash deploy/gcp/rt.sh audit`（只读）。逐项打 ✅ / ⚠️：Cloud Shell 里有没有留着私钥的文件、命令历史里有没有私钥；虚拟机有没有服务账号、有没有加固、项目里有哪些人有权限；虚拟机上设置文件的权限、**同一个设置名是不是写了不止一行**（服务只认第一行）、`/tmp` 有没有残留、**私钥是不是加密保存着、用的是不是 TPM、这台机器解不解得开**、**明文还在不在任何文件里**（设置文件、`/etc`、记录目录、程序目录、各用户目录、`/tmp`、`/var/log`，注释掉的旧行也算）、系统日志里有没有、是不是在进程的环境变量里、服务是不是从 systemd 拿到了它、服务是不是专用用户运行、不写 core dump、只在本机监听、有没有交换分区、SSH 是否只认密钥、自动安全更新、哪些账号能 sudo。私钥在虚拟机上当作搜索条件用（放在只有 root 能读的临时文件里，用完覆盖删掉），从不显示、也不传回 Cloud Shell。

### 需要你自己做的（按重要程度）

1. **Google 账号开两步验证**，最好用通行密钥或安全密钥（<https://myaccount.google.com/security>）。项目的 IAM 里只留你自己；不要创建、下载服务账号密钥。
2. **这个钱包里只放够用的钱。** 私钥被拿走的最大损失就是账户里的余额：按 `RULE_MAX_DAY_USD` 留几天的量，利润定期提走。和 Railway 共用同一个账户时，同一把私钥存在两个平台上，哪边出事都一样。
3. **GitHub 账号开两步验证**；仓库保持私有，不加不认识的协作者。
4. 部署完运行 `bash deploy/gcp/rt.sh lockdown`，并删掉 Cloud Shell 里的 `ruletaker.env`。私钥不要贴到聊天、截图、工单里。
5. **Telegram 账号开两步验证**（设置 → 隐私和安全）：管理员账号能暂停、恢复、切模式。
6. Google Cloud **设预算提醒**（结算 → 预算和提醒）：云账号被盗最常见的后果是被拿去开一堆机器挖矿。
7. **怀疑私钥泄露时**：马上在 Predict 网站把钱提到别的地址 → `bash deploy/gcp/rt.sh stop` → 换一个新账户。导出的私钥没法“改密码”，只能弃用。

没有做的：把私钥放进硬件密钥（KMS / HSM）里签名——每签一张单要多一次网络往返，和抢单的目标冲突；Secret Manager 对一个人的项目和现在的做法保护程度相同（都取决于 Google 账号），还多一个开机时要连的服务；开机输口令解锁——机器重启、服务崩溃自动重启时就没人输口令了，抢单会停。加固脚本（`lockdown`）和上面的流程用假的 gcloud 模拟验证过顺序和回滚，没有在真实的 Google Cloud 项目上跑过。

## 记录、恢复与风控

- **记录**：每场每个模式一条（真实 `rule:<场次链接>`，只记录 `rule:paper:<场次链接>`），存在虚拟机的 SQLite（`/var/lib/ruletaker/`）。格式和 huice 一样：订单哈希、成交份数、均价、手续费、结算结果、盈亏，以及每场的“盘口观察”（卖单什么时候出现、什么时候开始被吃、什么时候被吃光，按 Predict 盘口自己的时间戳）。
- **发单前先落盘**：每张真实订单在请求发出前，先把哈希写进数据库旁边的订单日志（`ruletaker.sqlite3.rule-orders`）。进程在发单途中崩溃或重启，启动时按哈希去 Predict 核对，**绝不重发**。应答丢失、超时、裸 409 都按“结果未知”处理，按哈希找回。日志写进去后由单独的线程马上刷到磁盘（fdatasync，和发单同时进行、不拖慢发单），机器断电也丢不了刚发出的单。
- **日亏损停机**：当天已结算的盈亏一到停机线就停，**当天之后再结算出盈利也不解除**（重启后仍然停着），第二天自动恢复；要当天继续，发 `/resume`——从那一刻的盈亏起再给一个额度。网页上把停机额度调低到已经亏过的线，也当场停。
- **风控**：每场份数、每天上限、日亏损停机、`LIVE_TRADING_ALLOWED` 硬开关、暂停（会保存，重启后仍然暂停）；运行中切换模式不能高于设置文件。发单前最后一刻（请求真正发出的那一刻；没有现成的连接、要先做 TCP/TLS 握手的话，握手之后再核一次）再核一次：设置是不是刚改过、是否暂停、是否就绪、**离开场是否已不足 15 秒**（盘中：离结束）、余额够不够（扣掉同时在途的其他单）、盘中指数是否还在规则方向。
- **余额**：链上读到的 USDT 扣掉读余额前后下的、成交的单可能已经花掉的钱（成交上链要几秒），再扣掉**所有还没了结的单**（挂着没成交完的、应答丢了结果未知的）没成交的部分——查单一直查不到也照样扣着，直到它签名里的到期时间（开场前 5 秒，盘中单是这一场结束前 5 秒；最后 2 分钟里下的单是开场 / 结束后 1 分 55 秒）过去 15 分钟后又读了一次余额：过了到期时间 Predict 不会再撮合它，那次余额里已经有它成交过的一切。几场同时有卖单时第二张单按剩下的钱下，不会被 Predict 以余额不足拒绝。
- **结算**：按这一场**实际买的那个结果**（它的 indexSet）判输赢，结果的名字是什么都行（例如“Up or Flat / Down”这种）；只有很早以前没存 indexSet 的记录才看结果名字，认不出就在 Telegram 报警一次、不按猜的结算。Predict 迟迟不结算的场次读得越来越少（结束 1 小时后每 10 分钟一次，1 天后每小时一次），不占下单要用的请求额度。
- **挂单测试同一时间只做一张**：Telegram 和网页同时点、或者连点两下，第二个只回“正在进行”；Telegram 确认卡上的“确定”只认一次，点下去先收起按钮再执行。
- **网络断了**：连接根本没建立（被拒、TLS 握手失败、超时）时一个字节都没发出，这张单记“没下成”，不占这一场的份数，2 秒后再看盘口重下；连上之后才出的错（发出去了没回音）才按“结果未知”按哈希核对。查单时 Predict 回了空内容，对已有订单号的单不当成“查无此单”，过一会儿再查，成交照样记全。
- **推送**：两条推送连接共用一份盘口版本号，一条重连不会让另一条已经送来的新盘口被旧的盖掉；版本号从头开始（盘口重建）时按 Predict 自己的更新时间认新旧。
- **只记录模式**：和真实下单守同一条线——读盘口花了时间、回来时已经过了开场前 15 秒（盘中：结束前 15 秒），这一笔不记，复盘里不会多出实盘做不到的成交。
- **数据库写不进去时不开新单**（例如磁盘满）：记录写不进去，重启后就找不到这张单，所以宁可不下；写入会一直重试，恢复后自动继续。
- **停止时**：在途订单最多等 25 秒应答，应答一到就撤掉没成交的部分（systemd 给停止留了 75 秒，平时一秒就停）。
- **私钥和账号**：见上一节“[安全](#安全)”。
- **地区和条款**：Predict 不向受限地区开放交易（受限地区读取正常、下单 403）。部署后先跑 `rt.sh check`；是否允许在当地使用请以 Predict.fun 的服务条款为准。

| `src/taker/` | 规则吃单本体：`look.rs`（看盘、定份数、签名、下单）、`orders.rs`（跟单、撤单、结算）、`flow.rs`（主循环、节奏、预热、核对、盘中）、`control.rs`（暂停 / 模式 / 自检 / 挂单测试 / 网页设置）、`text.rs`（状态文字） |
| `src/rules.rs` | 规则和场次、盘口换算、记录的统计、抢单记录 |
| `src/stream.rs` | Predict 盘口推送 |
| `src/predict.rs` | Predict REST 接口、限流节拍、链上读余额和授权、应答解析 |
| `src/wallet.rs` | 订单签名（EIP-712，Predict 账户的 Kernel 包装） |
| `src/index.rs` | 币安合约指数（盘中吃单用） |
| `src/http.rs` | 长连接 HTTP/1.1（TLS、连接池、断连检测、POST 绝不重发） |
| `src/store.rs` | SQLite 记录（和 Python 版同一个表、同一种格式） |
| `src/telegram.rs`、`src/server.rs` | Telegram、状态页和控制台的接口 |
| `src/console.rs`、`src/review.rs`、`web/console.html` | 控制台的设置、复盘的统计和 CSV、网页本身 |
| `src/config.rs`、`src/clock.rs`、`src/cards.rs` | 设置、纽约时间和 CME 日历、15 分钟市场 |
| `src/tests.rs`、`src/parity.rs`、`tests/vectors/` | 全过程测试、和 Python 版逐字节对照的数据 |
| `deploy/gcp/` | Google Cloud 部署脚本（`rt.sh`，含安全加固 `lockdown`）、systemd 服务、虚拟机安装脚本 |
| `Cargo.toml`、`Cargo.lock` | Rust 依赖；全部依赖的版本和哈希锁定 |
| `python/` | Python 版 2.0（备用）：`python/ruletaker/`、测试、`requirements.lock` |
